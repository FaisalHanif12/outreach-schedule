## 2. The 40-a-day ceiling was never the constraint

This is the thing worth being clear about, because it is the opposite of what the number 26
suggests.

```
Task 1 ceiling      25       created 7      floor 15   MISSED FLOOR by 8
Task 3 ceiling      15       created 12     floor 10   met floor, missed target by 3
Domain ceiling      40       created 19
```

Task 3 derived its ceiling correctly — `min(15, 40 − 7) = 15` — and then delivered 12 because it
ran out of qualifying businesses, not because it ran out of allowance. Neither task was ever
throttled. **Both ran out of supply.**

So raising the targets did not fail because 40 was too aggressive. It failed in Task 1's sourcing.

## 3. Task 1 — 7 against a target of 25. This is the real problem.

### What it delivered

- 5 follow-ups. **This is the designed maximum**, not a shortfall. Follow-ups are capped at 5.
- 2 new companies: Gooseworks and Uplift AI, both with a personally published address, both
  verified. **Quality was not the problem.**

### Why it stopped

Reading its own account of the run, the sequence was:

1. Spawned both permitted research subagents.
2. Waited for them. They returned **2 verified candidates from ~27 screened**.
3. Made **one** direct ATS sweep of its own.
4. Concluded: *"I've exhausted the productive research lanes for today with genuinely poor yield."*
5. Spent remaining budget re-examining two near-misses rather than opening new lanes.

**~118 companies screened against a budget of 230 planned and 280 absolute.** It did not come
close to spending what it was given. It stopped because the first two lanes were thin, not because
the work ran out.

### The instruction defect that allowed it

The prompt says:

> If 25 cannot be reached without lowering the evidence bar, DELIVER SHORT AND SAY SO — that is a
> correct outcome.

That rule is right, and it is why the 2 companies it did deliver are real. **But it is a last
resort written as though it were a decision available at any moment.** There is nothing in the
file that says *how much work must be done before "thin day" becomes an available conclusion.*
So the run reached for it after two subagents and one search.

Compare Task 3, which had no equivalent escape hatch phrased that way and worked five separate
regional lanes to get to 12.

### The fix

Add a **sourcing floor** to Task 1: an explicit list of lanes, with a rule that a thin day cannot
be declared until every lane has been attempted and at least 200 calls spent. Concretely:

```
1. YC company pages and launch posts
2. HN "Who is hiring" — current month AND previous month
3. Greenhouse / Lever / Ashby / Workable API slug sweeps
4. Funding news, last 14 days (press-release contact lines are the highest-yield
   source in this whole pipeline — every personal address in that lane on 7 August
   came from a "Media contact:" line)
5. npm / PyPI maintainer records
6. Public git commit author headers  (test once, it may be blocked)
7. Wellfound, WeWorkRemotely, RemoteOK
8. The "verified but NOT contacted" and "near miss" sections of the suppression list

YOU MAY NOT REPORT A THIN DAY UNTIL ALL EIGHT HAVE BEEN ATTEMPTED AND YOU HAVE
SPENT AT LEAST 200 CALLS. Report each lane's screened/verified counts separately.
```

Also worth changing: the run spent both subagents up front, then had none left when it needed
breadth. Better to source directly first and hold the subagents for the lanes that are genuinely
parallelisable.

## 4. Task 3 — 12 against a target of 15. Acceptable, with one inefficiency.

Regional split: **US 3 · UK 3 · Canada 2 · Australia 2 · EU 2.** All five regions produced. That
is the new design working on its first outing.

Three honest reasons for the gap, all recorded in its report:

- One Canadian candidate (Young Nail Bar) was **rejected for being too polished** — no genuine
  findings. That is the correct call.
- Two Geelong physio candidates were lost to **Cloudflare bot challenges** — site-side, correctly
  classified as unreadable rather than as a tool failure.
- EU sourcing cost more calls per lead, as predicted.

**The inefficiency:** call-lead sourcing consumed roughly **30 calls against a ~10 budget** before
landing 3 leads. That overspend came out of the website-lead budget, and it is plausibly the
difference between 12 and 14. All three call leads came back Grade 2 (localsearch microsite only),
in one city, Greenville SC.

Fix: cap call-lead sourcing at **15 calls, hard**. Deliver 2 leads rather than overspend for 3.

## 5. The failure that actually matters: git push was denied all day

Both runs hit `403 Resource not accessible by integration` on **every** write path — `git push`,
`push_files`, `create_or_update_file`, `create_branch`. Read access worked throughout. Task 1
diagnosed it twice from independent angles and correctly stopped retrying.

### What that cost

| Artefact | Status |
|---|---|
| Task 3 tracker, 7 → 22 rows | Sent to you as a file. **Recoverable.** |
| Task 3 packet + 15 preview pages | Sent to you as files. **Recoverable.** |
| Task 1 run report | Sent to you as a file. **Recoverable.** |
| **Task 1's updated `do-not-contact.md`** | **Committed only to an ephemeral branch and never sent. Gone with the container.** |

That last line is the one to act on. Task 1 made four changes to the suppression list that now
exist nowhere you can reach:

1. **Hugentic → `sent, REPLIED`** (the pending correction — it found and fixed it correctly)
2. Five rows → `sent, FOLLOWED_1_DRAFTED`: Airweave, Ambral, Artificial Societies, assistant-ui,
   Balance
3. **A new row for Gooseworks**
4. **A new row for Uplift AI**

**Until those are back in the file, tomorrow's run can send Gooseworks and Uplift AI a second
first-touch email, and can follow up the five 2-August companies a second time.** That is the
exact failure the suppression list exists to prevent.

### Fixing the permission

`github.com/settings/installations` → **Claude** → **Configure**. Two things to check:

- **Repository access** includes `outreach-schedule`.
- **Permissions** → **Contents** reads **Read and write**, not Read-only. If GitHub shows a
  pending permission request at the top of that page, approve it — a write scope added after
  install stays inactive until you do.

Then re-run Task 1 manually once and confirm the commit lands before tomorrow morning.

### The instruction defect this exposed

Neither routine treats "could not push" as a stop condition, so both completed and reported
success with a caveat. **A run whose state write did not land has not succeeded** — the next run
inherits a stale suppression list, which is the one thing the whole design is built to avoid.

Add to both files:

```
IF THE PUSH FAILS, THE RUN HAS FAILED.
Open the report IN CAPITALS with "STATE WRITE DID NOT LAND — NEXT RUN WILL SEE A
STALE SUPPRESSION LIST. DO NOT TRIGGER THE NEXT RUN UNTIL THIS IS PUSHED."
Then send the FULL updated state file as a file attachment, not just the report,
so the rows survive the container. Do this before writing the report.
```

Task 3 did send its tracker. Task 1 did not send its suppression list. That asymmetry is luck, not
design, and it should be written down.

## 6. Two smaller findings

**The HTML self-check does not work.** Task 1's step 7 verifies the shipped HTML via `get_thread`
with `messageFormat: FULL_CONTENT`. On a draft-only thread this returned a permission error, and
`list_drafts` did not return body content either. The run substituted an argument from
construction — every draft used `htmlBody` only, so the `google.com/url` rewrite cannot occur.
That reasoning is sound, but **the check is currently decorative and should either be fixed or
replaced with an explicit assertion that `body` was never passed.**

**No bounces, no replies, in either run.** Bounce rate 1% over the last 100 sends, under the 2%
threshold. The deliverability block worked as intended on its first outing.
